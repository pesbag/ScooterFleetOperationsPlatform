# Bike Fleet Operations Platform

מערכת תפעול אופניים ב־C# / ASP.NET Core 8, עם Razor Views ו־CSS ללא JavaScript. התשתיות נשארו MySQL, MongoDB, Kafka ו־Redis.

## פתיחה והפעלה

פתחו את `BikeFleet.code-workspace` ב־VS Code, או את `BikeFleet.sln` התואם ל־.NET 8. שירות הקליטה נמצא בתיקיית `Bike_fleet_operation_platform`.

```powershell
# רק אם אין קובץ .env: יוצר סיסמאות אקראיות מקומיות
powershell -ExecutionPolicy Bypass -File scripts/setup.ps1
# הפעלה / עדכון אצלך
docker compose up -d --build
```

האתר: http://127.0.0.1:8080. פרטי המנהל נמצאים ב־`.env` בשדות `SEED_ADMIN_EMAIL` ו־`SEED_ADMIN_PASSWORD`. המנהל נוצר רק במסד משתמשים ריק. סיסמה של חשבון קיים אינה משתנה בעת שינוי משתני ה־seed. הקובץ מוחרג מ־Git; אל תפרסמו אותו.

אין למחוק volumes. שמות מסדי הנתונים, נושאי Kafka ושמות volumes נשמרו כדי לא לפגוע במידע קיים. טבלאות הרוכבים והמדדים מתווספות דרך `OperationsSchema.Upgrade` ללא מחיקת טבלאות. נתוני מקורות קודמים אינם נמחקים; רק תחנות המקור הנבחר מוצגות.

## מקור אמיתי וקצב העדכון

המקור הוא [Citi Bike — System Data](https://citibikenyc.com/system-data), דרך [GBFS 2.3](https://gbfs.citibikenyc.com/gbfs/2.3/gbfs.json). המקור מדווח על אופניים רגילים וחשמליים. נשמרים שמות התחנות, קיבולת, מספר אופניים זמינים, מקומות החזרה וזמן הדיווח.

```text
GBFS_BASE_URL=https://gbfs.lyft.com/gbfs/2.3/bkn/en/
GBFS_STATION_PREFIX=citibike:
UI_REFRESH_SECONDS=60
APP_PORT=8080
```

מזהי המקור מקבלים תחילית פנימית `citibike:` כדי לא לערבב אותם עם מקורות קודמים. מזהה התחנה עצמו נשמר בתוך המזהה הפנימי. אין מחולל נתונים ואין מתג הדגמה בקוד הייצור. fixtures קיימים רק בבדיקות.

- הקליטה מבקשת סטטוס כל 60 שניות ומטא־דאטה פעם בשעה, לפי `Polling`.
- לכל משימת קליטה לולאה עוקבת ללא חפיפה. timeout וניסיונות חוזרים מוגבלים מוגדרים ב־`Http`.
- Kafka מעביר את ההודעות; המעבד שומר מטא־דאטה ב־MySQL וסטטוס/היסטוריה ב־MongoDB.
- ה־API משתמש במטמון Redis של 60 שניות בדיוק. כתיבת מידע חדש משנה את גרסת המטמון; שגיאת Redis מאפשרת קריאה ממסדי הנתונים.
- דפי תצוגה מתרעננים אוטומטית באמצעות HTML meta refresh, ללא JavaScript. אפשר להשהות את הרענון. טופסי הרשמה, דיווח ועריכה אינם מתרעננים אוטומטית.

זו מערכת המתעדכנת במחזורים, לא זרם מיידי. זמן המקור, עד דקה עד האיסוף, זמן העיבוד ועד דקה לרענון הדף משפיעים על ההשהיה. במקרה של אובדן פסילת מטמון ייתכן עיכוב נוסף עד תום 60 השניות. `ReportedAt` הוא זמן הדיווח של התחנה; `ReceivedAt` הוא זמן קבלת התגובה בשירות הקליטה. זמן יצירת הדף מוצג בנפרד.

בדיקת המקור אינה מוכיחה ש־Kafka, מסדי הנתונים והממשק המקומי מחוברים מקצה לקצה. את בדיקת Docker והנתיב המלא מבצעים אצלך.

## אמינות הנתונים ומצב התחנה

מידע חסר נשאר null. אפס מפורש הוא אפס. דיווח ישן מעשר דקות או לא תקין אינו מוצג כזמינות נוכחית ואינו מייצר המלצות. תחנה מאוזנת עם דיווח תקין תוצג כ־Healthy; תחנה שבאמת ריקה או כמעט מלאה יכולה להיות Critical. הדשבורד מציג את שש התחנות בעלות הסיכון הגבוה ביותר — אין להסיק מהן שכל הרשת קריטית.

קיבולת חסרה אינה מומצאת; עבור תחנה כזו לא מחושבים תפוסה, חיזוי מילוי והמלצת העברה. סך האופניים הזמינים אינו גודל הצי הכולל, משום שאופניים בנסיעה או בתחזוקה עשויים לא להיכלל.

מצב תחנה מפוצל לשלושה מושגים:

1. סיכון זמינות לפי דיווח הספק (`Status`).
2. מצב תקלות תחזוקה ודיווחי רוכבים (`MaintenanceStatus`, מספר תקלות פתוחות).
3. מצב תפעולי משולב (`OperationalStatus`), לצד מצב המשימה עצמה.

סגירת תקלה שומרת זמן ומשתמש, פוסלת את המטמון ומציגה מחדש את התחנה. תקלה נוספת נשארת פתוחה. השלמת משימה אינה מזייפת כמות אופניים; תחנה הופכת ל־Active כאשר הנתונים עדכניים ותקינים, השירות פתוח, הסיכון תקין ולא נשארו בעיות פתוחות. אם הספק עדיין מדווח על מחסור, מוצגת Attention עם ההסבר. התראה על סיכון מתמשך עשויה להיווצר מחדש לאחר תקופת ההמתנה המוגדרת.

## משתמשים ומסכים

- ADMIN: ניהול משתמשים, תחנות, התראות, משימות, דיווחים ומדדים.
- OPERATOR: תפעול, טיפול בדיווחים ומדדים; ללא ניהול משתמשים.
- RIDER: זמינות אופניים, חיפוש, מועדפים אישיים ודיווח תקלות.

הרשמה ציבורית יוצרת RIDER בלבד. סיסמאות נשמרות באמצעות ASP.NET PasswordHasher, עם cookie HttpOnly ו־CSRF. הרשאות נאכפות ב־API. ההרשמה אינה מבצעת כניסה אוטומטית. Logout זמין בכל דף מחובר; תוכן אישי אינו נשמר במטמון HTTP או ב־Redis המשותף.

Overview מציג סיכום; Stations מציג תחנות; Station מציג זמינות, היסטוריה וסטטוסים; Alerts מציג התראות; Rebalancing מציג משימות; Rider reports מיועד לטיפול בדיווחי רוכבים; Impact metrics מציג מדידה של התועלת.

## מדדים והסברים

זמן ריק נספר רק בין קריאות אפס סמוכות, ללא השלמה של פערי מידע. זמן תגובה נמדד מיצירת המלצה עד התחלתה. שיעור השלמה נמדד מתוך המלצות שנוצרו בשבעת הימים האחרונים. שגיאת תחזית היא MAE בכמות אופניים ל־30 דקות, עם מספר המדגמים. זמני תחזית מוצגים בשעות ודקות, עם עיגול כלפי מעלה ושמות יחיד/רבים.

שינוי בזמינות אחרי משימה נמדד מול קריאה 15–20 דקות לאחר ההשלמה; הוא אינו הוכחה לסיבתיות. מדדים מתחילים להצטבר עם נתונים אמיתיים. לא משחזרים זמני התחלה היסטוריים שלא נשמרו.

## בדיקות

```powershell
dotnet build BikeFleet.sln
dotnet run --project FleetTests
# מוסיף קריאה אמיתית מהמקור, ללא כתיבה ל־Kafka או למסדי נתונים
dotnet run --project FleetTests -- --gbfs
# לאחר שהפעלתם את המערכת אצלכם:
powershell -ExecutionPolicy Bypass -File scripts/smoke-test.ps1
```

הבדיקות המקומיות כוללות לוגיקה, עיצוב זמנים, תקלות HTTP, התנהגות מטמון עם Redis מדומה, רינדור Razor, רענון והרשאות. סקריפט smoke מפעיל API אמיתי ובודק הרשמה, כפילות, כניסה/יציאה, הרשאות, מועדפים ושתי תקלות בדיקה. הוא אינו משלים משימת העברה אמיתית, ובסיום משבית את חשבון הבדיקה וסוגר את הדיווחים שלו.

הסקריפט תלוי בכך שפרטי המנהל בקובץ `.env` תואמים לחשבון קיים. הוא אינו משנה סיסמאות קיימות. פירוט תוצאות ואי־ודאויות נמצא ב־`docs/IMPLEMENTATION_REPORT.md`.
